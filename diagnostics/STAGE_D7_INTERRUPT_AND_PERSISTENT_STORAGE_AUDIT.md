## 1. Executive Summary

This report delivers an exhaustive, source-proven audit of:
1. The hardware interrupt and event acknowledgment architecture, specifically resolving the long-standing silicon semantics of register `0x1A84`.
2. The persistent-storage blast radius of all vendor calibration, baseline, and arming procedures.

Our investigation establishes that register `0x1A84` is an authentic **Write-1-To-Clear (W1TC)** event acknowledgment register paired with `0x1A82` (event status) and `0x1A83` (event mask). The historical unconditional `write 0x1A84 = 0xFFFF` operations in startup code represent a "flush all pending latches" pattern safe only during cold reset; runtime code strictly reads `0x1A82` and echoes back the observed bits to clear only processed events.

Furthermore, our persistent storage audit conclusively confirms that **zero OTP, eFuse, EEPROM, or Flash write facilities are invoked anywhere in `fdt_baseline()`, `image_baseline()`, or `arm()`.** All operations execute in volatile SFRs and SRAM.

## 2. Interrupt Architecture & `0x1A84` Silicon Semantics

### 2.1 The Register Triad: Status, Mask, and Acknowledgment

The FocalTech FT9362 interrupt controller is organized around a 16-bit register triad located in the `0x1A8x` system control block:

```
  ┌─────────────────────────────────────────────────────────────────┐
  │ 0x1A82: Interrupt / Event Status Register (Read-Only)          │
  │ Latches hardware event flags generated by sensing subsystems.   │
  └────────────────────────┬────────────────────────────────────────┘
                           │ (Bits gated by Mask Register)
                           ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ 0x1A83: Interrupt / Event Mask Register (Read/Write)            │
  │ Bitwise enable mask controlling event routing to Pad 229 IRQ.  │
  └────────────────────────┬────────────────────────────────────────┘
                           │ (Write-1-To-Clear Acknowledgment)
                           ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │ 0x1A84: Interrupt / Event Acknowledge Register (W1TC)           │
  │ Writing 1 to a bit position clears that specific latch in 0x1A82│
  └─────────────────────────────────────────────────────────────────┘
```

### 2.2 Bitwise Mapping of the Event Triad

Synthesizing all bitwise manipulations across `fw9369_fdt.c`, `fw9369_release.c`, `capture.c`, and `ft93xx.c`, the 16-bit layout is decoded as follows:

| Bit Position | Hex Mask | Subsystem / Event Name | Source Citation & Demonstrated Behavior |
|---|---|---|---|
| **Bit 0** | `0x0001` | Touch Down (Finger Contact) | `fw9369_release.c:322`, `test-fte3600-fw9369-runtime.c:179` (down_status=2/1) |
| **Bit 1** | `0x0002` | Touch Up (Finger Removal) | `fw9369_release.c:322`, `test-fte3600-fw9369-runtime.c:179` (up_status=4) |
| **Bit 2** | `0x0004` | Navigation / Motion Flag | `ft93xx.c:1347`, `fw9369_release.c:286` (Linux mode routing bit) |
| **Bit 3** | `0x0008` | FDT Scan Conversion Ready | `fw9369_fdt.c:230` (`0x1A83 |= 0x08`), `fw9369_fdt.c:252` (`if (value & 8) OK`), `ft93xx.c:1094` (`write 0x1A84 = 8`) |
| **Bit 4** | `0x0010` | Auxiliary / Linux Event Gate | `fw9369_release.c:286` (`(0x1A83 & 0xFF80) | 0x0016`) |
| **Bit 5** | `0x0020` | Image FIFO Frame Available | `capture.c:170` (`0x1A83 |= 0x0020`), `capture.c:280` (`write 0x1A84 = 0x0020`), `ft93xx.c:483` (`if (word & 0x20) write 0x1A84, 0x20`) |
| **Bits 6..15** | `0xFFC0` | Unused / Reserved | Kept masked by default |

### 3.3 Hazard Analysis of `write 0x1A84 = 0xFFFF`

Writing `0xFFFF` indiscriminately asserts every bit in the W1TC register.
- **Why it is safe during cold startup:** During the startup prefix, the sensor has just emerged from hardware reset. No user is interacting with the device, and no touch interrupt is expected. A global flush guarantees the interrupt line is deasserted.
- **Why it is dangerous during runtime:** If issued while the sensor is actively monitoring for finger touch, writing `0xFFFF` will race against and annihilate a real touch-down or touch-up interrupt occurring on the same clock cycle, resulting in a dropped event and an unresponsive UI.
- **Kernel Policy Recommendation:** In any future kernel interrupt service routine (ISR) or workqueue, the driver **must strictly follow the `read_word(0x1A82) -> write_word(0x1A84, word)` pattern**, never issuing `0xFFFF` during runtime.

### 4.2 Non-Volatile OTP / eFuse Facilities

As established in Stage D6.1, the FT9362 silicon possesses OTP read facilities controlled via registers `0xF1`, `0xF3`, and `0xF4`.
- In `fw9369_startup.c`, lines 347–355 read the factory lot/foundry code from OTP into volatile driver memory during the startup prefix.
- **In `fdt_baseline()`, `image_baseline()`, and `arm()`, registers `0xF1`, `0xF3`, and `0xF4` are NEVER touched.**
- There are zero write operations targeting OTP address spaces anywhere in the calibration, baseline, or arming paths.
- There are no charge-pump enable sequences, no high-voltage programming strobes, and no non-volatile burn commands.

## 5. Audit Conclusions & Summary

1. **W1TC Semantics Confirmed:** Register `0x1A84` is definitively established as a Write-1-To-Clear event acknowledgment register. Runtime event handling must use the `read(0x1A82) -> write(0x1A84)` paradigm to avoid dropping concurrent asynchronous interrupts.
2. **Zero Persistent Storage Hazard:** All calibration and baseline procedures operate exclusively in volatile memory. No risk of bricking, altering silicon trim, or burning OTP exists during calibration or arming.
3. **Volatile Retention Reality:** Because all baseline data is stored in volatile host RAM and volatile sensor SFRs, any hardware power loss or active reset pulse completely invalidates sensor calibration, requiring a full re-calibration upon power restoration.
